- (note) Judging criteria: Agentic AI Design & Technical Execution; Innovation & Originality; Scalability & Responsible AI; Presentation & Clarity
- (decision) Portwatch will use genuine specialized sub-agents (not a single agent + if-engine) because tasks delegate more naturally across berth/crane/yard/AGV domains
- (lock) Architecture: 3 core specialist sub-agents (Berth/Vessel, Crane, Yard) + optional cut-first AGV/Gate agent, each independent LLM call with scoped least-privilege tools, run in PARALLEL with per-agent timeouts. Portwatch is a separate arbiter/synthesis agent that resolves conflicts across specialist outputs into Options A/B/C. Deterministic policy engine remains unchanged, gating the chosen option after synthesis.
- (lock) Confidence score is a deterministic computed formula (staleness_penalty + missing_data_penalty + disagreement_penalty + variance_penalty subtracted from 100), NOT an LLM self-reported number. Mirrors the 'policy engine separate from LLM' trust story. Weights are tunable heuristics, not claimed to be precisely calibrated -- defensible line if a judge asks.
- (lock) Team: 4 people, 6 days. Split: A=orchestration core (agents/arbiter/policy/confidence), B=mock services+timeout injection, C=frontend dashboard, D=integration/demo scripting/DG layer/pitch prep. Timeline: Day1-2 scaffolding, Day3 golden-path (Three-Way Disruption) runs end-to-end for real, Day4 dashboard wired to real backend, Day5 stretch-only additive (DG layer, AGV/Gate agent, gate congestion) must not touch golden path, Day6 rehearsal + recorded backup demo run in case live LLM calls flake.
- (lock) Headline differentiator (Innovation/Originality): promote DG (dangerous goods) IMDG segregation constraint from section-14-footnote to a core demo beat. Twist the Three-Way Disruption scenario so Portwatch's own recommended Option B is rejected by the deterministic DG safety check (segregation violation vs cargo already in target yard block), forcing a re-plan live in the demo. This is the one genuinely maritime-specific, non-generic element vs a hospital/airline/data-center incident-response template.
- (lock) Scalability: (1) Incident processor built as stateless-per-incident workers from Day 1-2 (no shared mutable state/locks) so concurrent incidents are structurally free, not bolted on. Day 5 stretch demo beat: trigger 2 simultaneous unrelated incidents live, show both resolve independently -- proves scalability instead of just claiming it via diagram. (2) Approval-bottleneck-at-scale (many Tier-3 escalations at once, e.g. typhoon) is NOT built; stated as a known limitation with a ready Q&A answer: escalations would be prioritized by predicted-impact/SLA-risk and batched by shared root cause -- framed as post-MVP future work.
