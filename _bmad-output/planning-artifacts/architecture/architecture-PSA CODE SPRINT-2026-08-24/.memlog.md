- (decision) Paradigm: single-process modular monolith, not microservices. Binds: all 4 build lanes (A orchestration, B mock services, C frontend, D integration) into one deployable backend + one frontend. Prevents: infra/deployment complexity (queues, containers, service mesh) burning build time in a 6-day hackathon.
- (decision) Stack: Python 3.12+ / FastAPI backend (verified current ~0.141, mid-2026), React + TypeScript + Vite frontend. Binds: Person A/B/D backend work to one language/runtime. Prevents: polyglot service boundaries needing their own contracts.
- (decision) Specialist agents (Berth, Crane, Yard) and Arbiter call the Anthropic Messages API directly (raw tool-use calls), not the Claude Agent SDK. Rationale: Agent SDK is built for autonomous coding-agent workloads (broad file/bash/subagent reach); Portwatch needs per-agent scoped tool access and a policy engine explicitly outside LLM authority (FR3, FR7, FR9 security note) -- raw API calls give exact control over which tool schemas each agent call can see. Prevents: an agent silently gaining tool access beyond its scoped role.
- (version) FastAPI ~0.141.x confirmed current as of July 2026 web search; stays sub-1.0 by design (semver breaking changes possible) but production-stable and widely used.
- (decision) State ownership: single-writer orchestrator pattern. One Incident object per incident_id (in-memory, held by that incident's async task) with an embedded append-only trace list. Binds: only the per-incident orchestrator coroutine may write/append to Incident state or trace; specialist agents, arbiter, policy engine, and mock services are called, return structured results, never mutate shared state directly; frontend (C) only ever reads Incident via API, never writes. Prevents: concurrent incidents or independently-built agents racing/double-writing shared state (violates FR16); gives FR14's trace as a natural byproduct of the orchestrator's control flow rather than separate bookkeeping; enforces least-privilege (agents have no reference to shared state to violate).
- (decision) Correlation: a central in-memory IncidentRegistry (keyed by entity: vessel/berth/crane/yard-block) is checked before dispatch on every incoming signal. Binds: ingestion layer must consult the registry (open incidents + their entities/timestamps) before creating a new Incident task; a match within the 15-min rolling window (FR2) feeds the signal into the existing incident's orchestrator instead of spawning a new one. Prevents: duplicate/parallel incidents for what should be one correlated event, and ingestion logic diverging on how correlation is decided.
- (decision) Frontend updates: polling (2-3s interval) against the read-only Incident API, not SSE/WebSocket. Rationale: NFR1's ~20-30s golden-path window makes a short poll interval indistinguishable from real-time for a live demo, and avoids Person C building/debugging a persistent-connection layer under 6-day time pressure. Binds: dashboard (status feed, trace view, Tier-3 approval card) all read via polling the same Incident read endpoint. Prevents: a push-based channel becoming a second, divergent way to read incident state.
- (decision) Kill switch (FR10): single global in-memory AtomicBool/flag, process-level, checked at exactly one enforcement point -- immediately before any mock-service execution call (Tier 1/2 auto-execute, or Tier 3 post-approval). Not checked at ingestion/correlation/analysis. Binds: execution layer (owned by D/A integration) must gate every mock-service call on this flag. Prevents: kill switch being checked inconsistently across code paths, or execution slipping through during the window between decision and action.
- (decision) Tool scoping (FR3, least-privilege): each specialist agent has a static tool manifest (config mapping agent name -> allowed tool schemas) passed into its Messages API call; enforced at the API-call boundary by which schemas are supplied, not by prompting/convention. Binds: Berth/Crane/Yard agent constructors must load from this manifest; adding agent capability means editing the manifest, not the prompt. Prevents: an agent gaining tool access outside its scoped role (e.g. Berth calling Yard Manager).
- (decision) DG/IMDG hard gate (FR9): fixed position in orchestrator flow -- runs after policy-tier classification (Tier 1/2/3), before execution, independent of tier. On conflict: loop back to arbiter for a new recovery option rather than proceeding, then re-run tier classification on the new option. Binds: orchestrator's stage sequence must include this check as a distinct step between 'policy decision' and 'execution' in the trace. Prevents: a DG violation slipping through because a tier was already approved.
- (decision) Deployment/environment envelope: local dev machines for build; single instance (localhost or one deployed box) for the live demo. No containers, cloud infra, or multi-environment setup -- this is a 6-day hackathon demo, not a shipped product. Production deployment strategy is explicitly Deferred, not decided here.
- (decision) [ADOPTED] Persistence: in-memory only for the demo session, no database. Source: PRD Out-of-Scope ('persistence beyond the demo session'). Binds: Incident state, registry, and trace all live in process memory and are lost on restart -- acceptable for a live demo. Prevents: a builder reaching for SQLite/Postgres out of habit and burning build time on schema/migrations not needed for the golden path.
- (decision) [ADOPTED] Auth: none. Single-user, no login/session management. Source: PRD Out-of-Scope ('Production auth'). Binds: dashboard and API assume one operator context, no per-user identity in the trace beyond a fixed demo persona. Prevents: building an auth layer the demo doesn't need.
- (decision) Tier-3 'modify' (FR11) scoped to selecting a different one of the arbiter's 2-3 presented recovery options (FR4), not free-form plan editing. Binds: approval-card API contract is approve / reject / select-alternative(option_id), not an open edit payload. Prevents: Person C building a generic plan-diff/edit UI not needed for the demo scenario.
- (decision) [ADOPTED] Yard Manager mock service models two terminal blocks (Tuas C7, Pasir Panjang P2) from the start, even though FR17's routing logic is Day-5 stretch. Source: PRD FR17 (reuses existing Yard Agent/arbiter/policy engine unchanged). Binds: Person B's Yard Manager interface returns per-block utilization from day 1, so FR17 is additive later rather than a schema change under time pressure.
